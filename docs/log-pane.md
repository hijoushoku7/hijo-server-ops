# ログペイン改修計画（折り返し・タイムスタンプ・スクロール）

## やりたいこと

1. 行を折り返す
2. resize で破棄されている行を破棄せず保存し、幅に合わせて表示する
3. スクロールを折り返しに合わせる
4. ログに短いタイムスタンプを追加し、色分けして見やすくする（プレイヤー名は別系統の色）

## 現状の問題

ターミナルを縮めるとログの右端が切れ、その状態で広げ直すと切れたまま右に空白が残る。

原因は「リサイズを検知できていない」ことではない。`tea.WindowSizeMsg` は既に
`model.resize()` に届いている（`internal/ui/model.go:150`）。問題は**行を保存する
時点で当時の幅に切り詰めて捨てている**ことで、元テキストが残っていないため広げても
復元しようがない。

該当箇所は 3 つ。

- `internal/ui/state.go:97,103,105` — `Add` の時点で `truncate(line, 現在の幅)` した
  文字列を保存している。以後この行の右端は永久に失われる。
- `internal/ui/state.go:74-75` — `resize` で `chat.Truncate()` / `logs.Truncate()` が
  保存済み文字列をさらに破壊的に上書きする。縮小のたびに削れていく一方通行。
- `internal/ui/view.go:181` — 描画側は `renderPanel` → `fitLine(line, innerWidth)` で
  既に truncate + パディングしている。つまり**保存時の切り詰めは冗長**で、害しかない。

拡大時に右に出る空白は `fitLine` のパディングであり、埋めるべき本文がもう存在しない。

## 実装順序

**A（項目 2）→ B（項目 4）→ C（項目 1 + 3）** の 3 フェーズ。各フェーズ 1 PR。

やりたいこと記載の順（1→2→3→4）で進めると、1 を作った直後に 2 と 4 が同じコードを
2 回書き直させることになる。

| 順 | 内容 | 前提にしているもの |
|---|---|---|
| A | レコード保存化・破壊的 truncate 除去・履歴消失バグ修正 | なし |
| B | タイムスタンプ・色分け | A のレコード構造 |
| C | 折り返し＋スクロールのアンカー化 | A の元データ、B のガター幅と「素テキストを折る」構造 |

## フェーズ A ＝ 項目 2（保存の作り直し）

### 最初に置く理由

1 も 3 も 4 も「行の元データが残っている」ことが前提で、今は残っていない。この土台
なしに折り返しを書くと、切り詰め済みの文字列を折り返すことになって無意味。

### 内容

- 保存を「表示用文字列」から**レコード**（時刻・kind・プレイヤー名・本文を分けて持つ
  構造体）に変える。単なる生文字列保存ではなくレコードにするのが要点で、これが
  フェーズ B・C 両方の前提になる。
- `lineBuffer` のリングバッファ機構自体は流用する。要素型のみ差し替える。
- `state.go` の `Add` 呼び出しから `truncate(...)` を外す。
- `lineBuffer.Truncate(width)` を削除し、`resize`（state.go:74-75）の 2 呼び出しも消す。
- 切り詰めは描画時のみ。既存の `fitLine` が担うので描画側の変更は原則不要。
- 保存長の上限: 上流の `cmd/hso/output.go` が 1 行 16KiB でキャップ済みだが、
  `historyLines = 500` × 2 バッファで理論上の最悪が数十 MB になる。バッファ側で
  保存上限（例: 1024 桁）に丸めておく。端末幅がそこに達することはないので今回の
  バグは再発しない。

### 同時に直すバグ

`resize` は `layout.ready` が false（最小サイズ 72x21 未満）のとき `SetLimit(0)` を
呼び、**履歴を全部捨てている**（state.go:68-73, buffer.go:44-51）。ウィンドウを一瞬
小さくしただけでログが消える。`history` は `ready` と切り離して常に `historyLines` を
渡す。表示行数 0 は `Window(viewport)` 側が既に処理している。

### 先に決めておくこと（タイムスタンプの出所）

現在 `serverlog.Entry` に時刻フィールドがなく、パーサは `[HH:MM:SS]` 前置きを
`logPrefixPattern` で捨てている。さらに `cmd/hso/output.go:60` で `entry.Raw = ""` して
いる。項目 4 のタイムスタンプはどこかから復活させる必要がある。

方針: **ログ由来の時刻を優先し、取れなければ hso の受信時刻**。レコードの形を決める
フェーズ A で同時に決める（後から足すと保存形式をもう一度変えることになる）。設計原則
4 に沿い、時刻の出所が違うことは区別できるようにしておく。

### この時点での見た目

変わらない（1 レコード = 1 行、右端で切る）。広げれば切れていた部分が戻る、という
挙動だけが直る。

### テスト

- 幅を縮めてから広げると、元の行が末尾まで再表示される
- 最小サイズ未満に縮めてから戻しても履歴が残っている
- 既存の `buffer_test.go:38` `TestLineBufferTruncatesWideCharacters` は削除

## フェーズ B ＝ 項目 4（タイムスタンプ・色分け）

### 折り返しより先に置く理由

1. **ガター幅がここで確定する。** タイムスタンプを左に置くと、折り返した 2 行目以降は
   その幅だけぶら下げインデントしないと、どこからが新しいログか分からなくなる
   （「行が分からなくなる」懸念の実体）。つまり折り返しは `width` ではなく
   `(1 行目の幅, 継続行の幅, インデント)` を受け取る関数になる。先に折り返しを作ると
   この署名で書き直しになる。
2. **色を後から足すと折り返しが ANSI 対応を強いられる。** 色付き文字列の折り返しは
   エスケープ列をまたぐ処理が必要でバグの温床。逆に「レコード → 素のテキストを
   折り返す → 各セグメントに色を付ける」の順にすれば、折り返しは**常に素のテキスト
   だけを扱う**。この構造を成立させるには色付けの責務が先に整理されている必要がある。

副次的に、B は単体で完結してすぐ効果が見えるので、リスクの高い C の前に一度安定した
状態を作れる。

### 内容

- タイムスタンプは `HH:MM` の 5 桁。ガターは区切りの 1 桁を足して 6 桁。秒まで出すと
  8 桁になり、狭い端末で本文を圧迫する。ログを追う用途では分単位で足りる
- kind ごとの配色（join / leave / chat / command / lag / other）
- プレイヤー名だけ別系統の色。名前のハッシュから固定色を割り当て、同じ人が常に同じ色に
  なるようにする
- 幅が足りないときはタイムスタンプを落とすフォールバック
- 既存の `internal/ui/theme.go` のプリセット機構に乗せる

## フェーズ C ＝ 項目 1 + 3（折り返しとスクロール）

### 1 と 3 を分けられない理由

折り返した瞬間「1 レコード ≠ 1 表示行」になり、現在の `offset`（最新から何行遡ったか）
の意味が壊れる。折り返しだけ入れてスクロールを据え置くと、スクロール量が見た目とズレた
壊れた状態が中間成果物として残る。同一 PR にする。

### 最後に置く理由

3 フェーズ中で唯一、既存の挙動（スクロール）を作り替える。A・B が済んでいれば、ここで
扱う問題は純粋に「レコード列 → 表示行列への写像」だけに絞られる。

### 設計の芯

**スクロール位置をレコードのアンカー `(レコード番号, 何セグメント目)` で保持し、表示行
オフセットは派生値にする。** 表示行番号で持つとリサイズのたびに見ていた場所が飛ぶ。
アンカーなら幅を変えても注目していたログが画面に残る。

加えて「末尾追従中（offset 0）」は特別扱いし、リサイズしても追従を維持する。

### その他ここで決めること

- 折り返し結果のキャッシュ。幅が変わらない限り再計算せず、レコード追加時は末尾だけ
  差分計算する
- `↑N` インジケータ（view.go:135-137）の単位を表示行に変更
- 1 レコードが画面高を超える場合、上端で途中から表示するのを許す（許さないと詰む）
- 折り返し位置は空白優先＋なければセル単位のハード折り。Minecraft のログはパスや JSON が
  多く、単語折りだけだと破綻する
- 全角文字は `ansi.StringWidth` ベースでセル単位に扱う
